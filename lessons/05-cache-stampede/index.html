Lesson 05 · Caching

The cache stampede

Caching your homepage query makes the database's life easy — 99% of requests never touch it. Then the cache key expires during peak traffic, and every request in flight suddenly misses at once. Five hundred copies of the same expensive query land on the database in the same second. That's a stampede, and it can take a healthy site down in one TTL.

~8 min readIntermediateRedis · TTL · thundering herd

The pattern everyone writes first

// cache-aside — the standard recipe
value = cache.get("homepage:feed");
if (value == null) {              // ← every concurrent request passes this together
  value = db.expensiveQuery();    // 800ms of joins
  cache.set("homepage:feed", value, ttl=60);
}
return value;

Ninety-nine percent of the time this is perfect: the key is warm, requests are served from memory, the database idles. The problem is the moment the TTL runs out. Expiry is instant and global — one millisecond the key exists, the next it doesn't, for everyone. Every request that arrives in the window before the first recompute finishes sees null, and each one independently decides to run the 800ms query. The busier your site, the more requests fit in that window — the stampede scales with your traffic, which is why it hits hardest exactly when you can least afford it.

The fix: one worker rebuilds, everyone else waits — or eats leftovers

1 · A recompute lock

On a miss, don't recompute immediately — first try to claim the right to recompute. Redis makes this a one-liner: SET … NX succeeds for exactly one caller. The winner runs the query; everyone else knows a rebuild is already in flight.

# exactly one request wins this — same atomic-claim move as Lessons 02 and 04
SET lock:homepage:feed 1 NX EX 10

2 · Serve stale while revalidating

What do the losers do while the winner rebuilds? The best answer: serve the old value. Don't actually delete data at expiry — keep it in the cache past its logical TTL and treat the TTL as "time to start refreshing", not "time to vanish". A feed that's 60 seconds out of date is invisible to users; a database at 100% CPU is not.

// store the value with its own logical expiry inside
entry = cache.get("homepage:feed");   // { value, freshUntil }
if (entry.freshUntil < now()) {
  if (acquireLock()) {
    refreshInBackground();             // ONE query, off the request path
  }
  return entry.value;                  // everyone gets a fast, slightly-old answer
}
return entry.value;

3 · Spread out the expiries

Stampedes also happen when many keys expire together — a deploy that warmed a thousand keys at the same moment schedules a thousand simultaneous expiries one TTL later. Add jitter: ttl = 60 + random(0, 10). Ten lines of blast radius becomes a gentle slope.

Spot the recurring move. Lesson 02 claimed an event ID with a unique constraint. Lesson 04 claimed the last item with an atomic UPDATE. Here you claim the recompute with SET NX. Different systems, same idea: when N workers race for one job, an atomic claim picks exactly one winner.
Locks need timeouts. Always set an expiry on the lock itself (EX 10). If the winning worker crashes mid-rebuild, the lock must free itself — otherwise the key stays stale forever and you've traded a stampede for an outage of a different flavor.

The takeaway

A cache doesn't just make reads fast — it stands between your traffic and your database, and expiry is the moment that shield drops. Never let a miss trigger unbounded concurrent recomputes: one lock so a single worker rebuilds, stale data for everyone else, jitter so keys don't expire in choirs. The database should feel a cache expiry as one query, not five hundred.
