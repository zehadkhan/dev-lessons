Lesson 11 · Networking

What happens when you type a URL

The classic interview question — answered as a latency budget you can see: DNS → TCP → TLS → HTTP → first byte. Every step is a network round-trip to somewhere, and whether each one is cold or warm decides if your site feels instant or sluggish.

~9 min readBeginner–IntermediateDNS · TCP · TLS · HTTP

Five steps, and your page is the last one

You press Enter on https://example.com. Before a single pixel of the page exists on your machine, the browser has to complete a relay race — five legs, each one a round trip to somewhere:

  • DNS resolution — turn the name into an IP address. The browser asks a resolver, which may have to walk the whole DNS hierarchy to find the answer.
  • TCP three-way handshake — SYN, SYN-ACK, ACK. One full round trip to the server before either side can send a byte of data.
  • TLS handshake — negotiate ciphers, verify the certificate, agree on keys. Classically up to two more round trips before the connection is private.
  • HTTP request — finally, GET / travels to the server.
  • Server think-time + response — the server renders, queries, computes… and the first byte of your page comes back.

Notice what that list means: the bytes of your page are the last step. Everything before it is pure overhead — ceremony to figure out where the server is and how to talk to it safely. And overhead has a beautiful property that page bytes don't: it can be cached or reused. A resolved name can be remembered. An open TCP connection can be kept alive. A TLS session can be resumed. The whole craft of fast websites starts with deleting round trips you already paid for once.

Read the waterfall yourself

You don't need devtools to see this budget — curl can print every checkpoint. Each variable is a cumulative timestamp, so the difference between consecutive lines is the cost of that phase:

$ curl -sS -o /dev/null -w 'namelookup:    %{time_namelookup}s
connect:       %{time_connect}s
appconnect:    %{time_appconnect}s
starttransfer: %{time_starttransfer}s
total:         %{time_total}s
' https://example.com

# cold run — compare with the waterfall above:
namelookup:    0.121s   # DNS done
connect:       0.166s   # + TCP handshake (~45ms)
appconnect:    0.257s   # + TLS handshake (~90ms)
starttransfer: 0.512s   # + request + server think-time → FIRST BYTE
total:         0.523s   # + reading the rest of the body

Run it twice in a row (with curl's connection reuse, or from a browser) and watch namelookup, connect and appconnect collapse toward zero — that's the warm path in the widget, measured for real.

This lesson is the map, not the territory. Each of the expensive steps gets its own deep-dive: Lesson 12 zooms into DNS and how a stale TTL takes your site down, Lesson 13 opens up the TCP handshake and what happens when connections pile up, and Lesson 14 walks through TLS — including the expired-certificate outage every on-call engineer eventually meets.
Where CDNs fit. Every bar in the waterfall is proportional to the distance between you and the machine you're talking to. Move the server from another continent to a datacenter 20ms away and every round trip shrinks at once — DNS, TCP, TLS, and the request itself. That's the real superpower of edge caching, and it's why CDNs get a whole chapter of their own later in the roadmap.

The takeaway

Performance intuition is mostly counting round trips. Before the first byte of your page, a cold visitor pays for DNS, a TCP handshake, a TLS handshake, and the request itself — in our run, ~300ms of ceremony before the server even started thinking. The warm visitor pays for almost none of it, and that cold-versus-warm gap is the difference users actually feel. Keep-alive connections, DNS TTLs and TLS session resumption aren't obscure tuning knobs — they exist specifically to delete steps 1–3 from the budget. When a page feels slow, don't start by guessing: pull up the waterfall, find the widest bar, and ask which round trips you're paying for that you've already paid for before.
