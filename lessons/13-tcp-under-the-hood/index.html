TCP under the hood

TCP promises a reliable, ordered byte stream over a network that guarantees neither. The price of that promise is round trips and retransmissions — which is why packet loss makes applications feel SLOW, not broken, and why "the network is fine, ping works" can be true while your app crawls.

~9 min readIntermediateHandshake · retransmission · loss

What TCP actually does

Underneath every HTTP request, IP delivers packets the way a toddler delivers mail: maybe, in any order, possibly twice, possibly never. Everything you experience as "a connection" is manufactured on top of that chaos by TCP, running entirely in the two endpoints:

  • Connection setup via the three-way handshake — SYN → SYN-ACK → ACK. One full round trip is spent before any data moves. Every new connection pays this tax.
  • Sequence numbers — every byte is numbered, so the receiver can reassemble segments into the exact order they were sent, no matter how the network scrambles them.
  • ACKs — the receiver continuously tells the sender what has arrived. Anything sent but not acknowledged is presumed to still be in flight — or gone.
  • Retransmission timers — when an ACK doesn't come back in time, a timer (the RTO) fires and the sender resends. Lost packets are recovered by waiting, then repeating.
  • Ordering has a dark side — because the stream must be delivered in order, a lost packet blocks everything behind it. Later segments can arrive perfectly and still sit in a buffer, undeliverable, until the gap is filled. That's head-of-line blocking.

Notice what's not in that list: speed. TCP buys reliability with time. Every mechanism above is a round trip, a timer, or a wait — and that's exactly where the next incident comes from.

The incident: "the network is fine" but the app crawls

A path between your app servers and an upstream API starts dropping 2% of packets — a flaky optic, a congested peering link, an overloaded router. Here's the trap: 2% packet loss does not mean 2% of requests fail. Almost nothing fails. Instead, every lost segment costs a retransmission delay — hundreds of milliseconds to a full second of pure silence — and one request is made of many segments, so the odds of at least one loss per request are far higher than 2%. Losses hit the handshake too, and a lost SYN is the most expensive packet of all: the client knows nothing yet, so it waits a full conservative timeout before retrying.

Meanwhile: users report "it's slow", dashboards are green because nothing is erroring, and the on-call runs ping — which sends one tiny packet per second and mostly succeeds — and declares the network fine. Everyone is telling the truth. Everyone is wrong.

Prove it in production

Two tools turn "it feels slow" into evidence. First, mtr — traceroute and ping fused, per hop, with statistics — tells you where the loss lives:

# where is the loss? run enough cycles for 2% to show up
$ mtr --report --report-cycles 100 api.example.com
HOST: app-01                        Loss%   Snt   Last   Avg  Best  Wrst
  1.|-- 10.0.0.1                     0.0%   100    0.4   0.5   0.3   1.2
  2.|-- core-rtr-2.dc.example        0.0%   100    0.9   1.1   0.8   3.4
  3.|-- edge-19.transit-isp.net      2.0%   100    8.2   9.7   7.9  84.1  ← loss starts here…
  4.|-- ix-peer-7.transit-isp.net    2.0%   100   11.3  12.0  10.8  90.2  ← …and persists…
  5.|-- api.example.com              2.0%   100   14.1  14.9  13.6  95.5  ← …to the destination

# reading it: loss at ONE middle hop that vanishes downstream is usually a
# router deprioritizing its own ping replies — noise, ignore it. Loss that
# starts at a hop and persists all the way to the end is real loss ON the path.

Second, ss -ti asks the kernel what TCP itself is experiencing on live sockets — retransmission counters and round-trip estimates that no application log will ever show you:

# what is TCP living through right now? ask the socket
$ ss -ti dst api.example.com
State   Recv-Q  Send-Q   Local Address:Port     Peer Address:Port
ESTAB   0       0        10.0.4.11:53422        93.184.216.34:443
     cubic wscale:7,7 rto:412 rtt:104.5/38.2 mss:1448 cwnd:4
     bytes_sent:812311 retrans:2/47 lost:2 bytes_retrans:66608

# retrans:2/47 → 2 segments being retried right now, 47 retransmits over this
#                 socket's lifetime — every single one was a stall a user felt
# rtt:104.5/38.2 → smoothed RTT 104 ms, variance 38 ms — a jittery path
# rto:412        → the next loss costs a 412 ms silent wait before TCP resends
#
# and the "ping works" trap, spelled out:
#   ping     → one tiny 64-byte packet per second; at 2% loss, 98 of 100
#              succeed and the summary looks healthy
#   your app → bursts of full-size segments, and EVERY request needs its
#              whole burst to survive in sequence — loss taxes bursts, not pings
You've met this handshake before. The TCP bar in Lesson 11's waterfall is exactly this SYN → SYN-ACK → ACK round trip. HTTP keep-alive exists precisely so you pay it once per connection instead of once per request — and on a lossy path, reusing warm connections is the cheapest optimization you'll ever ship.
Head-of-line blocking is TCP's deepest limitation. TCP sees one ordered byte stream, so one lost packet stalls everything behind it — including all the streams an application multiplexes onto that connection. HTTP/2 ran headfirst into this: many parallel requests on one TCP connection, and a single lost packet froze all of them. That's the problem HTTP/3 (QUIC) was built to fix, by giving each stream independent delivery over UDP — a future chapter.

The takeaway

Reliability isn't free — TCP buys it with round trips and timers. A handshake before any data, an ACK for everything, a timeout for every silence: that's the invoice for turning an unreliable network into a dependable byte stream. So when an application is slow but nothing is erroring, suspect loss and retransmission — the failure mode that hides inside green dashboards. And measure it with mtr and ss -ti, because ping answering cheerfully proves almost nothing about what your bursts of real traffic are surviving.
