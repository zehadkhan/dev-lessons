MCP: how AI gets hands on your systems

A language model knows everything in general and nothing about your systems: not your database, not your logs, not last night's failed orders. Ask anyway and it may answer confidently — and wrong. The Model Context Protocol (MCP) is the open standard that fixes this: one protocol that lets any AI app discover and call tools you expose, instead of a custom integration for every app-tool pair.

~10 min readIntermediateMCP · JSON-RPC · tool calling

The smartest intern with no badge

An LLM is like a brilliant new hire on day one: it can explain replication lag from Lesson 08 better than most engineers, but it cannot answer "how many orders failed last night?" — it has never seen your database. Worse, models are trained to be helpful, so instead of a hard "I can't know that," you sometimes get a plausible, specific, fabricated answer. A hallucinated order count pasted into a status report is a production incident of a different kind.

The obvious fix is to give the model access — a "tool" it can call. And that worked, but before MCP every AI app invented its own way to do it. Connecting M AI apps to N internal systems meant M × N custom integrations, each with its own glue code, auth handling and format. MCP collapses that to M + N: each app speaks MCP once, each system exposes an MCP server once, and any app can talk to any system. Think USB-C for AI tools.

Three roles, one wire format

  • Host — the AI application the user talks to (Claude Code, a chat app, your own agent).
  • MCP server — a small program that exposes capabilities: tools (functions the model can call), plus optionally resources (readable data) and prompts. It wraps your system — a database, an API, a filesystem.
  • MCP client — lives inside the host; maintains one connection per server and relays messages.

On the wire it's JSON-RPC 2.0 — the same request/response-with-ids pattern you'd recognize from any RPC system. Two transports matter: stdio (the host launches the server as a child process and pipes JSON over stdin/stdout — perfect for local tools) and Streamable HTTP (the server is a remote endpoint — how hosted servers like GitHub's or Linear's work).

The conversation on the wire

Three moves: handshake, discovery, call. First the client and server agree on capabilities:

// client → server: handshake
{ "jsonrpc": "2.0", "id": 1, "method": "initialize",
  "params": { "protocolVersion": "2025-06-18", "clientInfo": { "name": "claude-code" } } }

// client → server: what can you do?
{ "jsonrpc": "2.0", "id": 2, "method": "tools/list" }

// server → client: my tools, with JSON Schema for the inputs
{ "id": 2, "result": { "tools": [ {
    "name": "failed_orders",
    "description": "Count and list failed orders in the last N hours",
    "inputSchema": { "type": "object", "properties": { "hours": { "type": "integer" } } }
} ] } }

The tool list — names, descriptions, schemas — goes into the model's context. When the user asks something a tool can answer, the model emits a call, the client relays it, and the result flows back into the conversation:

// client → server: the model decided to call the tool
{ "jsonrpc": "2.0", "id": 3, "method": "tools/call",
  "params": { "name": "failed_orders", "arguments": { "hours": 24 } } }

// server → client: real data from the real database
{ "id": 3, "result": { "content": [ { "type": "text",
    "text": "3 failed orders: #8112 ($49), #8117 ($120), #8123 ($15)" } ] } }

That's the whole protocol core. The description and schema are how the model knows when and how to call your tool — write them like documentation for a very literal colleague.

Build one: a server in 20 lines

The official SDKs make servers tiny. Here's the orders server from the animation, in Python — the decorator turns the function signature and docstring into the tools/list entry automatically:

# server.py — pip install "mcp[cli]" psycopg
from mcp.server.fastmcp import FastMCP
import psycopg, json, os

mcp = FastMCP("orders-db")

@mcp.tool()
def failed_orders(hours: int = 24) -> str:
    """Count and list failed orders in the last N hours."""
    with psycopg.connect(os.environ["DATABASE_URL"]) as conn:
        rows = conn.execute(
            "SELECT id, amount FROM orders WHERE status = 'failed' "
            "AND created_at > now() - make_interval(hours => %s)", (hours,)
        ).fetchall()
    return json.dumps({"count": len(rows), "orders": rows})

if __name__ == "__main__":
    mcp.run()  # stdio transport — the host launches this as a child process

Connect it to a host

# Claude Code — one command, then just ask about failed orders
$ claude mcp add orders-db --env DATABASE_URL=postgres://readonly:...@db/prod \
    -- python server.py

# Most other hosts use the same JSON shape in their config file:
{ "mcpServers": { "orders-db": {
    "command": "python", "args": ["server.py"],
    "env": { "DATABASE_URL": "postgres://readonly:...@db/prod" } } } }

Remote servers skip the config entirely — the host connects to a URL over Streamable HTTP, and the Claude API can do the same server-side via its MCP connector (mcp_servers on the Messages API), so your backend can give Claude tools without running any local process.

Notice the read-only user in that connection string. An MCP server runs with whatever credentials you give it, and the model decides when to call it. Same principle as every lesson before this one: don't trust the caller to be careful — make the dangerous thing impossible. A reporting tool gets a read-only DB user; a tool that writes gets the narrowest grant that works.
Two failure modes to respect. First: models retry. If a tool call times out and the model tries again, a create_refund tool that isn't idempotent double-refunds — Lesson 02's idempotency-key pattern applies to AI tools exactly as it does to webhooks. Second: tool results enter the model's context, so a malicious string in your data ("ignore previous instructions and…") becomes a prompt-injection attempt. Treat third-party MCP servers like any dependency: read the code, pin the version, and keep write-capable tools behind confirmation.

The takeaway

An AI without tools can only talk about your systems — and will sometimes make things up when you ask anyway. MCP is the standard socket: a server advertises tools with schemas (tools/list), the model calls them (tools/call), and answers come back grounded in real data instead of plausible fiction. One protocol instead of M × N integrations — and because the server is just your code, everything you already know applies: least-privilege credentials, idempotent writes, and never trusting input, even when the "user" is a model.
