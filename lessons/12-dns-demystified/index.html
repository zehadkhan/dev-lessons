Lesson 12 · Networking

DNS, demystified

DNS is a distributed, aggressively cached phone book — and almost every DNS incident is really a TTL incident. "Waiting for propagation" is mostly a myth: records don't spread anywhere. What you're actually waiting for is thousands of caches you told, in the record itself, to remember the old answer.

~9 min readIntermediateResolvers · records · TTL

How a lookup actually works

When you resolve example.com, the question climbs a chain. Your OS's stub resolver asks a recursive resolver (your ISP's, or a public one like 1.1.1.1 / 8.8.8.8). If the recursive resolver doesn't already know, it walks the hierarchy: the root servers say "ask the .com TLD servers", the TLD servers say "ask this domain's authoritative nameserver", and the authoritative server — the only machine that actually owns the answer — returns the record. Then the crucial part: the answer is cached at every layer — recursive resolver, OS, even your browser — for exactly as long as the record's TTL (time-to-live, in seconds) says. Until that timer expires, nobody re-asks.

The records you'll actually touch:

  • A / AAAA — name → IPv4 / IPv6 address. The workhorse.
  • CNAME — alias: "this name is really that name" (www → apex, app → CDN hostname).
  • MX — where this domain's mail goes.
  • TXT — free-form text: SPF/DKIM, domain-ownership proofs.
  • NS — which nameservers are authoritative for the zone.

The migration where half your users vanished

You've just finished the server move from Lesson 01's zero-downtime cutover. The new box is warm, the data is synced, and the last step looks like the easiest one: update the A record from the old IP to the new one. You click save in your DNS provider's dashboard, the record changes instantly on the authoritative nameserver — and nothing else happens.

Because the record had TTL 86400 — 24 hours. Every recursive resolver that answered a query in the last day is holding a cached copy of the old IP, and it will keep serving it, without ever contacting your nameserver, until its own copy of that 24-hour timer runs out. Users trickle over one expired cache at a time. Then someone decommissions the old server "because the DNS change is done" — and every user whose resolver still remembers the old IP gets a connection error. Support tickets say "site down". Your monitoring, which watches the new server, says all green.

See it yourself with dig

The TTL column is right there in every answer — most people just never look at it. Query twice and watch the cached copy count down:

$ dig A example.com

;; ANSWER SECTION:
example.com.    86400   IN  A   203.0.113.10   ← TTL: cache me for 24h

$ dig A example.com   # 90 seconds later — same resolver

;; ANSWER SECTION:
example.com.    86310   IN  A   203.0.113.10   ← counting down: this is a
                                                  cached copy, not a fresh answer

+trace skips every cache and walks the hierarchy the way a cold recursive resolver would — root, TLD, authoritative:

$ dig +trace example.com

.               518400  IN  NS  a.root-servers.net.    ← root: "ask the .com servers"
com.            172800  IN  NS  a.gtld-servers.net.    ← TLD: "ask the domain's NS"
example.com.    86400   IN  NS  ns1.yourdns.com.       ← delegation to authoritative
example.com.    300     IN  A   198.51.100.7           ← the authoritative answer

And the playbook that makes the widget's green run work — the whole trick is doing step 1 a day early:

# The TTL-lowering playbook
#
# 1. T-24h   lower the TTL: 86400 → 300     # old 24h answers must age out first,
                                          # so do this at least one OLD-TTL early
# 2. T-0     change the record: A → 198.51.100.7
# 3. T+5min  every cache has expired and re-queried → converged
# 4. T+1day  raise the TTL back to 86400   # low TTLs mean more queries hitting
                                          # your nameservers — don't leave it low
"Propagation" is mostly a myth. Your record doesn't spread across the internet — nothing pushes it anywhere. Caches simply hold the old answer until their TTL expires, then ask again. The only true propagation is your DNS provider syncing the change between its own authoritative nameservers, and that takes seconds. When a "propagation checker" shows different answers around the world, you're looking at caches in different countries expiring at different times.
The gotchas that survive a perfect playbook. Some ISP resolvers ignore very low TTLs and clamp them upward (a few minutes is respected almost everywhere; 5 seconds often isn't). Negative caching bites too: NXDOMAIN — "this name does not exist" — gets cached just like a real answer, so if you query a record before creating it (or typo it), the "doesn't exist" answer lingers for the zone's negative TTL. And your OS and browser keep their own caches on top of everything — the reason "it works on my phone but not my laptop" is a thing.

The takeaway

DNS changes are not slow — caches are obedient. The authoritative record updates the instant you save it; everything after that is resolvers respecting a timer you chose, possibly months ago. So treat TTL as part of the change, not a default you inherit: lower it a full old-TTL before any cutover, verify with dig that the low TTL is what caches are now receiving, make the change, watch traffic converge in minutes, then raise it back. And never decommission the old endpoint until the old TTL has fully expired — the caches don't know your migration plan.
