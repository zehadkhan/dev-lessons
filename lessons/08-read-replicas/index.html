Lesson 08 · Scaling

Read replicas and the vanishing write

One database can't serve all your traffic forever, and most traffic is reads. The standard move: keep one primary for writes, add replicas for reads. It works — and then a user updates their profile, the page reloads, and their change is gone. It isn't gone. They just read it from a database that lives a moment in the past.

~9 min readIntermediateReplication · lag · consistency

The architecture, in one paragraph

All writes go to the primary. The primary records every change in its binlog, and each replica replays that stream to stay a near-perfect copy — the same mechanism Lesson 01 used to migrate a server, now running permanently. Your app sends INSERT/UPDATE to the primary and spreads SELECTs across the replicas. Reads scale horizontally: need more read capacity, add another replica.

# the routing rule most frameworks give you out of the box
writes  → primary
reads   → replica-1, replica-2, …  # round-robin

The catch: replicas live in the past

Replication is fast but not instant — the replica is typically some milliseconds behind, and under heavy write load or a long-running query, that can stretch to seconds. Most reads never notice. The one that always notices: a user reading back their own write. Save profile → write lands on the primary → page reloads → read goes to a replica that hasn't replayed the write yet → the user sees their old name and hits save again, or files a bug, or trusts you a little less.

The fix: read your own writes from the primary

You don't need every read to be perfectly fresh — you need the writer's next few reads to be. That's a routing rule, not an architecture change: after a user writes, pin that user's reads to the primary for a short window (or until the replica catches up to that write). Everyone else keeps enjoying cheap replica reads.

// after any write, remember when — in the session or a cookie
onWrite(user) { session.lastWriteAt = now(); }

// route reads based on it
function dbForRead(session) {
  if (now() - session.lastWriteAt < 5s) return primary;   // fresh enough to matter
  return replica;                                       // everyone else: cheap reads
}

Frameworks ship this as "sticky primary" (Rails calls the delay window exactly this; ProxySQL and Django routers do the same). The precise version — wait for the replica to reach the write's binlog position (WAIT_FOR_EXECUTED_GTID_SET) — buys exactness at the cost of latency; the time-window version is what most teams run.

Two more rules that keep replicas honest

  • Monitor the lag, not just the replica. Seconds_Behind_Source (familiar from Lesson 01) belongs on a dashboard with an alert. A replica 10 minutes behind is quietly serving 10-minute-old prices.
  • Reads inside a write transaction go to the primary. A transaction that reads, decides, and writes (like Lesson 04's stock check) must see current data — never let the router send those reads to a replica.
The replica is also your standby. The same replica that scales your reads is a hot copy of your data — if the primary dies, you promote it (STOP REPLICA; SET read_only = OFF) and point writes at it, exactly like Lesson 01's cutover night, just unplanned. How that promotion happens under live traffic is the next lesson.
Replication is not a backup. A replica faithfully replays everything — including your accidental DELETE FROM users, about 200 milliseconds later. Replicas protect you from hardware dying; only real backups protect you from you.

The takeaway

Read replicas buy nearly unlimited read capacity by giving up one guarantee: that a read sees the very latest write. For almost all reads nobody can tell. For the one case where someone can — a user reading back their own write — route them to the primary for a few seconds. Scale like the replica is always behind; correctness only requires that writers never notice.
