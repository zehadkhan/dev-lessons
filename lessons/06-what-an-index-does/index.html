Lesson 06 · Database

What an index actually does

"Add an index" is the first advice every slow query gets, and most developers apply it as a magic word. But the mechanism is simple enough to watch: without an index the database reads every row and checks it; with one, it plays a guessing game it wins in four moves. Once you've seen both, EXPLAIN output stops being hieroglyphics.

~7 min readBeginner-friendlySQL · B-trees · EXPLAIN

The query that gets slower every week

SELECT * FROM users WHERE email = 'sam@example.com';

With no index on email, the database has exactly one strategy: read every row in the table and compare. This is a full table scan. It cannot stop early either — nothing guarantees there's only one Sam, so it checks all N rows every time. At 1,000 rows nobody notices. At a million rows, every login on your site quietly reads a million rows to find one. The query didn't change; the table grew under it. That's why unindexed queries feel like they "got slower for no reason" — the reason is Tuesday's new signups.

How the index wins: a sorted tree

An index is a second structure the database maintains next to your table: all the values of one column, kept sorted, arranged as a B-tree. Sorted data unlocks the same trick you use to find a word in a dictionary — you don't read from page one, you open near the middle and halve the search space each move. A B-tree does this with fat nodes that match disk pages, so a million rows are reachable in three or four page reads. Ten million? Four or five. The tree gets wider, barely deeper — that's why the indexed line in the animation stays flat while the scan line grows with the table.

Creating one is a one-liner

CREATE INDEX idx_users_email ON users (email);

Proof, before and after: EXPLAIN

EXPLAIN shows the plan the database chose. The two columns to read first are type and rows:

-- BEFORE: full scan
EXPLAIN SELECT * FROM users WHERE email = 'sam@example.com';
type: ALL          key: NULL          rows: 998,244

-- AFTER: index lookup
type: ref          key: idx_users_email   rows: 1

type: ALL means "I will read the whole table." If you see it on a query that runs per-request, that's your fire alarm.

Why not index everything, then?

  • Writes pay for reads. Every INSERT and UPDATE must also update every index on the table. A table with eight indexes does nine writes per insert.
  • Indexes only help queries that match their shape. An index on (email) does nothing for WHERE name = …, and a leading-wildcard LIKE '%@gmail.com' can't use it either — you can't binary-search a dictionary for words ending in "-tion".
  • Composite order matters. An index on (user_id, created_at) serves "this user's recent posts" beautifully, but is useless for a query filtering only on created_at. Left-to-right, like a phone book sorted by last name then first.
This is Lesson 03's other half. The N+1 lesson was about firing too many queries; this one is about each query doing too much work. A page can be slow for either reason — the query log tells you which: many fast queries is N+1, few slow ones is a missing index. EXPLAIN settles it in one line.
Index the columns you filter, join and sort by — and stop there. Your WHERE clauses, your foreign keys, your ORDER BY columns. If no query uses a column to narrow results, an index on it is pure write tax.

The takeaway

A full scan grows with your data; a B-tree lookup grows with the logarithm of your data, which in practice means it doesn't grow at all. When a query is slow, don't guess — run EXPLAIN, look for type: ALL on a big rows count, and give the database the sorted structure it needs to stop reading a million rows to find one.
