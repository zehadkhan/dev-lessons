Lesson 07 · DevOps

Deploys that can't take the site down

Every team eventually ships a build that starts, listens, and crashes on the first real request. The question isn't whether that build gets written — it's whether your deploy process lets it reach all of your servers at once. Here's the difference between a deploy that becomes an outage and one where users never notice.

~9 min readIntermediateLoad balancers · health checks · rollback

The big-bang deploy

The naive script is beautifully simple: push the new version to every server, restart everything. And when the build is good, it works. The problem is that it makes the health of your site equal to the health of your latest build — your worst build decides your uptime. A bad migration, a missing env var, a dependency that only breaks under real traffic: whatever slips past CI now runs on 100% of your fleet simultaneously, and the first person to find out is a customer.

The three ingredients of a safe deploy

1 · A real health check

The load balancer needs a way to ask each server "are you actually able to serve?" — not "is the process running?". A good /healthz endpoint exercises the app's critical path: it should touch the database connection, not just return 200 from a static handler. A server that fails the check gets no traffic; that single rule is what makes everything else safe.

# nginx upstream — a failing server is ejected automatically
upstream app {
  server 10.0.0.1:8080 max_fails=2 fail_timeout=10s;
  server 10.0.0.2:8080 max_fails=2 fail_timeout=10s;
  server 10.0.0.3:8080 max_fails=2 fail_timeout=10s;
}

2 · One server at a time

The rolling recipe, per server: drain it (stop sending new requests, let in-flight ones finish), deploy v2, run the health check, and only if it passes, return it to the pool and move to the next. The moment a health check fails, the deploy stops — v2 never reaches servers 2 and 3, and the bad build has a blast radius of zero traffic.

# the loop, spelled out
for srv in server-1 server-2 server-3; do
  lb drain  $srv          # stop new traffic, finish in-flight
  deploy v2 $srv
  healthcheck $srv || { rollback $srv; exit 1; }  # bad build stops HERE
  lb attach $srv
done

3 · A rollback that's boring

Keep the previous release on disk (a releases/ directory with a current symlink is the classic) so rollback is "point the symlink back and restart" — seconds, not a rebuild. A rollback you can run without thinking is the difference between a non-event and an incident call.

Blue-green is the same idea, bigger grain. Instead of rolling server by server, you keep two full environments — blue (live) and green (idle) — deploy to green, test it with real health checks while it takes zero traffic, then flip the load balancer. Rollback is flipping back. Rolling trades less hardware for a mixed-version window; blue-green trades double the servers for an instant, total switch. Lesson 01's migration cutover was blue-green with extra steps.
The mixed-version window is real. During a rolling deploy, v1 and v2 serve side by side for a few minutes. Your database schema and your APIs must tolerate both — add columns before code that needs them, never rename-and-drop in one release. If v2 can't coexist with v1, a rolling deploy just breaks you slowly instead of quickly.

The takeaway

You can't guarantee every build is good — CI catches most bad ones, never all. What you can guarantee is that a bad build meets a health check before it meets a user. Deploy to one server, ask it if it's healthy, and let "no" stop the line. Uptime stops depending on your best-case build and starts depending on your process — which is the only thing you fully control.
