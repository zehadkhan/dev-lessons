Lesson 09 · Reliability

Surviving a server crash at peak traffic

Servers die. Out-of-memory kills, kernel panics, a full disk, a cloud host that simply vanishes — at some point one of yours will stop mid-request on your busiest day. The difference between a five-second blip and an hour-long outage isn't luck. It's whether the system was built to expect the crash.

~9 min readIntermediateFailover · health checks · capacity

The setup nobody plans to have

A lot of production systems are one crash away from an incident because recovery depends on a person: the process dies, the monitoring (maybe) fires, someone (hopefully) sees it, SSHes in, and restarts things. Every minute of that chain is downtime — and traffic doesn't wait. Worse, if the dead server was one of two and the survivor can't carry the full load, the crash cascades: the second server buckles under doubled traffic and now everything is down.

Handling a crash gracefully takes three layers, each answering a different question:

  • Detection — who notices, and how fast? (A load balancer health check: seconds. A human: minutes to hours.)
  • Rerouting — where does the dead server's traffic go, and can the survivors carry it?
  • Recovery — who brings the dead server back? (A supervisor like systemd: seconds. A human with SSH: however long the coffee takes.)

Building the self-healing version

1 · Health checks eject the dead server in seconds

Same mechanism as Lesson 07, different trigger: there it caught a bad deploy, here it catches a crash. The load balancer probes every server every few seconds; two failed probes and the server is out of rotation. Users behind a health-checking LB experience a crash as a few seconds of slow or retried requests, not an outage.

# nginx: after 2 failures, stop routing there for 10s, then re-probe
server 10.0.0.2:8080 max_fails=2 fail_timeout=10s;

# and retry the request that hit the dead server on the next one up
proxy_next_upstream error timeout;

That second line matters: the request that was in flight when the server died gets retried on a healthy server instead of surfacing as a user-facing error. (Safe for reads and idempotent handlers — which is one more reason Lesson 02's pattern pays off.)

2 · A supervisor restarts the process — no human in the loop

# systemd unit — the crashed process is back in seconds
[Service]
ExecStart=/usr/bin/node server.js
Restart=always
RestartSec=3

If the whole machine died rather than just the process, this is where cloud autoscaling groups earn their keep: the group notices a missing instance and boots a replacement from an image. Either way the principle is identical — recovery is a mechanism, not a person.

3 · Capacity headroom: plan for N−1

Rerouting only works if the survivors can absorb the load. If three servers each run at 90%, losing one pushes the others to 135% — the crash cascades and the failover made things worse. The rule: run your fleet so it survives losing one server (~60–65% peak utilization on three servers). That "wasted" third is what you're actually buying when you buy redundancy.

What if it's the database that dies? Same three layers, heavier machinery. Detection: replication monitoring. Rerouting: promote the replica from Lesson 08 to primary and point the app at it — Lesson 01's cutover, unplanned. Recovery: rebuild the old primary as the new replica. Tools like Patroni or RDS Multi-AZ automate the whole dance; the moving parts are exactly what you've already seen.
Test the crash on purpose. A failover path that's never run is a failover path that doesn't work — the config typo, the security group, the DNS TTL all wait for the real incident to reveal themselves. Kill a server in staging (or, when you're brave, production at low traffic) and watch. If the system heals, you've proven it; if not, you found out on your terms.

The takeaway

"The server crashed" should be an entry in a log, not a story your team tells. Get a machine to notice (health checks), a machine to reroute (the load balancer), a machine to recover (a supervisor or autoscaler), and enough headroom that the survivors can carry the load. Humans are for fixing the root cause tomorrow morning — not for being the failover mechanism at 2am.
