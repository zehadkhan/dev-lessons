The N+1 query, seen live

You write a loop that looks completely reasonable: fetch some posts, then show each author's name. It works perfectly with 5 rows in development. In production with 500 rows it quietly fires 500 extra database queries and your page crawls. This is the N+1 problem — the most common performance trap in any ORM — and once you can see it, you'll spot it everywhere.

~7 min readBeginner-friendlyORM · SQL · performance

The innocent-looking code

Here's the trap. Fetch a list, then access a related record inside a loop:

// 1 query: get all posts
posts = Post.all();

// looks harmless...
for (post of posts) {
  print(post.author.name);  // ← fires a NEW query every loop
}

That last line is the problem. post.author is a related record the ORM hasn't loaded yet, so it silently runs SELECT * FROM authors WHERE id = ? — once per post. One query to get the posts, then N more for the authors. N posts + 1 = N+1 queries. The ORM makes it invisible because each individual query is tiny and the code reads like plain object access.

The fix: eager loading

Instead of letting the ORM fetch authors one at a time, tell it up front that you'll need them. The ORM then loads all the authors in a single follow-up query using WHERE id IN (…). Two queries total, forever — whether you have 5 posts or 5,000.

Laravel

// with() tells Eloquent to eager-load the relation
$posts = Post::with('author')->get();
// → 2 queries: one for posts, one for all authors

The two queries it actually runs

SELECT * FROM posts;
SELECT * FROM authors WHERE id IN (1, 2, 3, ...);  -- all at once
Why two queries beat N+1. Each database round-trip has fixed overhead — network hop, query parse, connection handling — often a millisecond or more, even for a trivial lookup. 500 tiny queries pay that tax 500 times. One IN query pays it once and lets the database do what it's good at: fetching many rows in a single scan.

How to catch it in your own app

  • ▸Turn on your framework's query log in development — Laravel Debugbar, Django Debug Toolbar, Rails' Bullet gem. A page that fires 200 queries is unmissable once you're counting.
  • ▸Any time you access a relation inside a loop, pause. That's the signature. The fix is almost always to eager-load the relation before the loop.
  • ▸Watch nested relations too — post.author.company in a loop can be N+1 twice over. Eager-load the whole chain: with('author.company').
Don't over-correct. Eager-loading a relation you never use just wastes memory and query time the other direction. Load what the page actually renders — no more, no less.

The takeaway

N+1 hides because it works fine on small data and each query is individually cheap. It only bites at production scale, which is the worst time to discover it. The habit that saves you: whenever you touch a related record inside a loop, eager-load it before the loop. Two queries, flat forever.
