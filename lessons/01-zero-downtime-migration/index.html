Lesson 01 · DevOps

Zero-downtime server migration

You need to move a live site — 500GB of files and a MySQL database that's being written to every second — onto a completely new host. The rule from the client: don't lose a single row, and keep downtime to minutes. Here's the pattern that makes it safe, animated end to end.

~10 min readIntermediateMySQL · rsync · replication

The trap everyone falls into first

The obvious plan is: take a database dump, copy the files, restore everything on the new server, switch DNS. It works right up until you notice the problem — anything written to the old database after you took the dump is gone. A customer places an order during the copy, and that order never makes it to the new server. For a 500GB site the copy alone takes hours, so that's a very wide window to lose data in.

The fix is to stop thinking of it as one big copy-and-switch, and instead split it into three moves: a bulk copy while the site stays live, a live replica that keeps the new database in sync in real time, and a tiny cutover window at the end where almost nothing is left to do.

The four moves, in commands

0 · Prep the new server (old one stays live)

Install the same stack — matching web server and, crucially, a MySQL version that is the same or newer than the old one. A dump taken on a newer MySQL will not always restore onto an older one.

Survival rule: run every long command inside tmux. If your SSH drops mid-transfer, the process keeps running on the server — you just reconnect and reattach. Without it, a dropped connection kills a 3-hour copy at 90%.
# on the new server
tmux new -s migration

1 · Bulk-copy the files while live

Copy the bulk of the 500GB now, with the site still serving. The -P flag is what makes this safe to interrupt: if it dies, run the exact same command again and it resumes — already-copied files are skipped. Exclude logs and cache; there's no reason to ship gigabytes of old log files.

rsync -avzP --exclude='storage/logs' --exclude='storage/framework/cache' \
      /var/www/html/ root@NEW_IP:/var/www/html/

2 · Dump and restore the database

Take a consistent snapshot without locking the site. --single-transaction gives you a clean point-in-time view of InnoDB tables without blocking writes, and --source-data=2 records exactly where in the binary log the snapshot was taken — you'll need that position in the next step.

mysqldump -u root -p --single-transaction --source-data=2 \
      --routines --triggers --quick app_db | gzip > dump.sql.gz

3 · Turn the new database into a live replica

Point the new server's MySQL at the old one, starting from the binlog position the dump recorded. From this moment the new database follows every write on the old one in real time. A tunnel keeps the connection encrypted so you never expose the database port publicly.

# new server follows old, starting at the recorded position
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='127.0.0.1', SOURCE_PORT=3307,
  SOURCE_USER='repl', SOURCE_LOG_FILE='mysql-bin.000003', SOURCE_LOG_POS=157;
START REPLICA;

Check it's caught up. These three lines are the whole game:

Replica_IO_Running:  Yes
Replica_SQL_Running: Yes
Seconds_Behind_Source: 0

4 · Cutover night

Pick a low-traffic hour. Now — and only now — does the site go down, and only for minutes:

  • Put the old site in maintenance mode so writes stop. This is the one non-negotiable step: it freezes the source so nothing can slip through during the switch.
  • Run a final rsync — only the handful of files that changed since the bulk copy. Seconds, not hours.
  • Confirm the replica shows Seconds_Behind_Source: 0.
  • Promote the replica: STOP REPLICA, turn read_only off — it's a standalone database now.
  • Switch DNS to the new server. Behind Cloudflare this is effectively instant.
  • Test, then turn maintenance off. You're live.
Don't delete the old server yet. Keep it running for a week or two after cutover. If anything looks wrong on the new host, pointing DNS back at the old one is your instant rollback — and it still has every row.

Why this loses zero data

The dump captured a consistent point in time. Replication carried every write after that point onto the new server continuously. And maintenance mode guaranteed no new writes happened during the final switch. There is no gap for a row to fall into — the three moves overlap so that every write is accounted for by at least one of them.
