Lesson 02 · Payments

Idempotent payment webhooks

Your payment provider sends a webhook when a customer pays. Simple — until the same event arrives twice and your customer gets charged twice. This isn't a bug in your code so much as a fact of how webhooks work. Here's why duplicates happen, and the one pattern that makes every retry harmless.

~8 min readIntermediateWebhooks · idempotency · races

Webhooks are "at least once", never "exactly once"

Every serious payment provider — Stripe, PayPal, Apple — promises to deliver a webhook at least once. That word "least" is doing a lot of work. If your server is slow to respond, times out, or returns a 500, the provider assumes you didn't get it and sends it again. Sometimes the first one actually did arrive and finish; you just answered too slowly. Now the same payment.succeeded event is in your queue twice.

If your handler naively does "insert a payment row, extend the subscription" every time it's called, two deliveries mean two payment rows and, worse, two charges. This is one of the most common — and most expensive — mistakes in payment integrations.

The fix: an idempotency key

Every webhook carries a unique event ID (evt_8f2a…). The fix is to treat that ID as an idempotency key: before doing any work, record that you've seen this ID — and if you've seen it before, stop immediately.

1 · A table that enforces uniqueness

The real guarantee lives in the database, not your code. A unique constraint on the event ID means even two requests racing at the exact same millisecond can't both win — the database rejects the second insert.

-- the unique index is the actual safety mechanism
CREATE TABLE processed_events (
  event_id   VARCHAR(255) UNIQUE NOT NULL,
  created_at TIMESTAMP DEFAULT now()
);

2 · Claim the event before processing

Try to insert the event ID first. If the insert fails on the unique constraint, a duplicate got here first — you return 200 OK and do nothing. Returning 200 is important: it tells the provider "received, stop retrying."

// pseudo-code — same shape in any language
try {
  db.insert('processed_events', { event_id: event.id });
} catch (UniqueViolation) {
  return 200;  // already handled — safe no-op
}
processPayment(event);  // only the first delivery reaches here
return 200;

3 · Wrap it in one transaction

Claim the event and record the payment in the same database transaction. If processing fails halfway, the whole thing rolls back — including the claim — so the provider's retry can safely try again. Half-done state is what turns a retry into a double charge.

Why the DB and not a cache? An in-memory check ("have I seen this ID?") looks like it works until two requests read "no" at the same instant and both proceed. Only a unique constraint in the database is atomic enough to win that race every time.
Also verify the signature. Before trusting any webhook, verify its cryptographic signature against your endpoint secret. Idempotency stops duplicates; signature verification stops forged events. You need both.

The takeaway

You can't stop your payment provider from sending duplicates — that's by design, and it's what makes delivery reliable. What you can do is make your handler not care: process each event ID exactly once, enforced by the database, inside a transaction. Do that and every retry, every timeout, every network hiccup becomes a harmless no-op.
