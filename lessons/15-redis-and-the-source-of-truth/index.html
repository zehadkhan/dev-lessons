Lesson 15 · Caching

Redis is not your source of truth

Watch one race registration go from click to confirmation, step by step. Then, one at a time, kill Redis, kill an app server, and kill the Postgres primary — and see what each failure actually costs. The rule that holds it all together: no registration data ever lives only in Redis. The truth is in Postgres.

~10 minIntermediatePostgres vs Redis · failure drills

Three places, three jobs

Postgres is the source of truth — durable, on disk, copied to three places, and never the thing you're allowed to lose. Redis exists purely for speed: cache, counters, sessions, queues — everything in it can, in principle, be rebuilt from Postgres. The standby and the R2 backup exist for disaster recovery. Follow the journey below, then start killing things one at a time and watch which of those three jobs actually breaks.

        Why Redis being wrong doesn't lose data

        1. Postgres commits first, everything else follows. SMS, email, and the queue all happen after the commit.
        2. No registration data is ever kept only in Redis. Redis holds counts, sessions, cache, and queues — nothing else.
        3. If Redis is empty or unreachable, sales stop. We never guess — a paused sale beats an oversold one.
        4. The count is fixed by counting the real rows in Postgres. If the count column and the rows disagree, the rebuild halts instead of copying a wrong number.
        5. When Redis's memory fills up, only the cache gets evicted — never the counts (volatile-lru, maxmemory 3gb).
        6. Postgres's CHECK constraint is the last wall. Even if Redis gets it wrong, the database itself blocks overselling.
        7. Copied in three places: primary, standby (~0.2s behind), and R2 — hourly dumps plus continuous WAL.
        Still open, honestly:
        • The sweep that catches lost SMS/email jobs hasn't been built. It's the one real gap that comes from Redis.
        • No failure drill has been run with Redis turned off, so how long restart and rebuild actually take is unknown.
        • Redis runs on a single server with no replica. If it dies, sales pause — but no data is lost.
        • Promoting the standby when the Postgres primary dies is a manual runbook, and it's never been rehearsed.

        The takeaway

        Redis earns its place by being fast and, when it matters, disposable. The instant you let it hold a fact that can't be rebuilt from Postgres, it stops being a cache and becomes a second, unguarded source of truth — and every one of its crashes turns from "sales paused for a few seconds" into "data gone". The architecture above holds that line everywhere except one spot — the SMS/email queue — and it says so plainly instead of pretending the gap doesn't exist.
