Lesson 04 · Concurrency

The inventory race condition

One item left in stock. Two customers click "Buy" in the same instant. Your code checks the stock, sees 1, and sells it — twice. Nothing crashed, no error was logged, and you now owe someone an item you don't have. This is check-then-act, the classic race condition, and the fix is one atomic query.

~8 min readIntermediateTransactions · locking · races

The code that looks correct

Almost every store starts with a handler shaped like this:

// check…
item = db.query("SELECT qty FROM stock WHERE id = 42");
if (item.qty > 0) {
  // …then act
  db.query("UPDATE stock SET qty = qty - 1 WHERE id = 42");  // ← the gap is above this line
  createOrder();
}

The bug lives in the gap between the SELECT and the UPDATE. Your server handles requests concurrently — that's the whole point of a web server. If two requests both run the SELECT before either runs the UPDATE, both see qty = 1, both pass the check, and both sell the item. The window is only microseconds wide, which is exactly why it never happens in testing and absolutely happens on launch day.

Watch the race happen

Run the check-then-act version and watch requests A and B interleave: both read 1, both pass, stock goes negative. Then run the atomic version and watch the database referee the race — one winner, one clean "out of stock".

The fix: let the database referee

You cannot close the gap from application code — two processes can always interleave between your read and your write. What you can do is collapse the check and the act into one statement, because a single SQL statement is atomic: the database applies it to one request at a time, full stop.

1 · The atomic conditional update

-- check and act in ONE statement — no gap to race through
UPDATE stock SET qty = qty - 1
WHERE id = 42 AND qty > 0;

Then look at the affected-row count the database hands back. One row affected means you won — create the order. Zero rows affected means someone beat you to it — return "out of stock". No exception handling, no lock management, just arithmetic the database guarantees.

// pseudo-code — same shape in any language
rows = db.execute("UPDATE stock SET qty = qty - 1 WHERE id = 42 AND qty > 0");
if (rows === 1) { createOrder(); return 200; }
return 409;  // sold out — cleanly, honestly

2 · When you need more than a decrement: row locks

If the "act" is genuinely multi-step — reserve stock, apply a coupon, write three tables — put it in a transaction and lock the row up front with SELECT … FOR UPDATE. The second request blocks at the lock until the first commits, then re-reads and sees the truth: qty = 0.

BEGIN;
SELECT qty FROM stock WHERE id = 42 FOR UPDATE;  -- B waits here until A commits
-- check qty, write orders, whatever you need — the row is yours
UPDATE stock SET qty = qty - 1 WHERE id = 42;
COMMIT;
Same principle as Lesson 02. The idempotency-key pattern and this one are the same move in different clothes: stop trusting application-level "have I checked?" logic and let a database guarantee — a unique constraint there, an atomic statement or row lock here — decide the race. The database is the only referee that sees both requests.
A constraint as the last line of defense. Add CHECK (qty >= 0) to the column (or an unsigned type). If a future refactor reintroduces the race, the database rejects the write instead of silently going negative — you get a loud error instead of a quiet oversell.

The takeaway

Any time your code does read, decide, write against shared data, another request can slip between the read and the write. Testing won't catch it; the window is too small. The fix is never "check more carefully" — it's to make the check and the write one atomic operation, in the one place that serializes everything: the database.
